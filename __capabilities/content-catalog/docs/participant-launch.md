# Participant launch server contract

Composition registers participant consumers through `server/participant-launch.mjs`. New operations use `registry.resolve({action, target})`; the target must declare the matching consumer. To keep an older implementation available for saved receipts, register it with `registry.register({consumer, authorizeDirectAccess, retainedOnly: true})`. Its matchers do not participate in new-operation resolution. Exact `registry.get({id, version})` and its direct access factory remain available; ordinary registrations still reject overlapping matchers.

Direct access factories authorize the stable target, action, and viewer, and return an authorized `{store, scope_key}`. They must not trust the target declaration as authority. On a direct retry or resume, the service selects an exact declared version and validates its matcher before invoking the factory, without resolving the current catalog. A genuinely new attempt resolves the current target inside the store callback.

The launch store checks an admitted request ID and digest before invoking its callback. Its `reserve` callback may return a validated `passthrough` when an optional direct consumer has no default context. The store returns this value without creating a request mapping or launch receipt. Required consumers fail in that case. A completed or pending admitted request remains recoverable if its default later disappears.

`ParticipantSetupResolver` is the common read-only selection and preparation path for launch and Admin validation. Inspect never retains artifacts. A new admission checks the effective setup hash before the consumer's retention hook, and the store commits the immutable snapshot, request mapping, and execution key atomically. The consumer executes after the store releases source locks. Explicit resume reads the retained snapshot, requires its exact registered version, and invokes that consumer's resume method; it does not resolve the live source or create a replacement execution.

For Agenda composition, `server/agenda.mjs` exposes its provider, codec, ledger, repository, and Admin validation adapter. The injected authority must authorize household, series, plan, item, action, and viewer for retained access. The ledger serializes series then activity and assumes one installed writer. It is an execution receipt, not a game-state store.

Party Games resumable discovery requires its injected `executionPort.inspect(sessionId, viewer)` to return an authorized, read-only runtime projection. It must never repair snapshots or write journals. If a Gaming receipt needs discovery and this port is unavailable, discovery fails with `participant_discovery_unavailable`; it never falls back to the potentially repairing `resume` operation. Explicit resume still uses `executionPort.resume` and may perform normal recovery.

The Agenda ledger records the newest admitted launch as preferred and returns its receipt first for automatic discovery. Starting a new launch never deletes older receipts; explicit resume remains scoped to the selected launch.

A provider returns its safe `returnTo` as part of the public source contract. Before retaining artifacts, the shared service validates and copies it into the store's `provenance.return_to`; provider-owned `provenance` is an optional serializable extension for internal evidence and cannot override that destination. Stores retain that provenance and return the validated destination from `readRetained`.

Participant validation errors expose a stable `code` and `field`. Source rosters use `participants.<index>...`; shared source selectors use `selector`, `selector.mode`, or `selector.keys[.<index>]`. Direct consumer defaults use `participantContext.participants`. Agenda Admin preserves roster paths at the plan root and translates selector paths to the relevant `activity_settings.<item_uid>.participants` binding (with `keys` mapped to `ids`).

### HTTP boundary

Composition mounts `createParticipantLaunchesRouter` at `/api/v1/participant-launches` with the installed household ID and the shared service. The JSON POST endpoints `inspect`, `begin`, and `resume` accept the corresponding service inputs except `viewer`, which comes from the authenticated request. `describe` accepts an action and direct target and resolves that target through the installed authoritative resolver before consulting the registry. Inspection and description do not admit a launch. Consumer-specific authorization, including the Party Games host requirement, remains with the registered consumer and provider.

Agenda composition mounts `createAdminAgendasRouter` at `/api/v1/admin/content/agendas` and `createPeopleRouter` at `/api/v1/admin/people`. These Admin surfaces require a host and derive household scope from composition. Series and plan reads and writes return strong ETags; updates and transitions require `If-Match`. Plan creation takes `weekOf`, `requestId`, and `sourceRevision`, plus `sourcePlanId` for a copy. Guest search returns the directory revision as an ETag; guest create, update, and archive use it as their precondition and return the affected identity. Plan validation accepts `{plan}` without saving. A missing precondition returns 428, a stale revision or conflicting request ID returns 409, field errors return 422, and unavailable installed features return 503. The installed runtime mounts these routers and the generic participant API when the opt-in Agenda configuration is enabled. Disabled endpoints report feature unavailable.

Agenda navigation composition imports `AgendaContentAdapter` and `AgendaMenuProjector` from the Agenda `server/content.mjs` public entry. Supply the projector with the shared `ListMenuProjector`, the Agenda ref codec, the same authoritative `resolveTarget` and participant consumer registry used by publication and launch. Supply the adapter with a repository, server clock, and `resolveHousehold({viewer,seriesId})` that enforces installed access. Register the adapter with the content source registry. It has listable capability and no flatten or queue method. A registered navigation-only source needs `source`, `prefixes`, `getItem`, and `getList`; playback and siblings are optional methods.

The list router accepts an injected `viewerForRequest(req)` for server-established viewer context. Its browse and gateway ports forward that value and the negotiated `participantLaunchVersion` (`1` only for the exact version header, otherwise `null`) to source `getList` only when the source declares `acceptsListContext: true`; legacy sources receive their original single argument. The response may carry `revision`, `notice`, `preview`, `adminUrl`, `disableAutoCountdown`, `navigationPolicy`, and `fixedOrder`. Rows may carry `disabled` and a `participantLaunches` map keyed by action; its values are typed opaque references, never roster or setup. Private source projections use `private, no-store` and vary by protocol, Authorization, and Cookie. The menu host must enforce disabled rows, disable countdown, retain the selected plan and focus on return, and send the protocol header only when it supports participant-aware actions. Composition and host installation are separate integration work.

### Browser composition contract

`frontend/src/composition/participants/index.js` exports the browser client, action dispatcher, launch host, and browser registry factory. Composition registers an adapter by adding `{consumer: {id, version}, outputSchema, render}` to `createParticipantBrowserRegistry` where `render` is a React component. The ready result is matched by the exact consumer ID, version, and output schema. The component receives only `{participantLaunch, clear}`; the result contains the explicit consumer context and output, while the host consumes and removes `return_to`. It must validate its own output payload and attach the already-created runtime, never re-run the unresolved menu reference. For an app adapter that renders `AppContainer`, register the same `{consumer, outputSchema}` in that app's `APP_REGISTRY` entry as `participantLaunch`, and pass the ready result explicitly. AppContainer forwards it only on an exact match. Party Games is registered as the production consumer with an exact adapter and app opt-in.

Optional passthrough registration uses `passthrough: Component` on the same browser entry. It receives only `{action, target, clear}` from the typed server result and must map that canonical target to the consumer's ordinary flow. It receives no inherited context or menu selection. A missing consumer, output schema, or passthrough adapter fails closed. Queue children inherit nothing implicitly.

Agenda's public `browser/screen.mjs` is the screen host entry; `browser/launch-services.mjs` exports the same host for composition. It negotiates protocol 1 using the established authenticated/device/context headers and passes the resulting menu to the existing MenuStack. It keeps the selected dated menu object stable while an activity is open, refreshes the dated ID on return, and preserves item UID focus. The service's validated `return_to` can select the retained dated target. Host errors present Retry/Back; no second navigation provider or player is installed.

Initial admission uses `intent: 'open'`, including a confirmed Start, so the service can reuse a matching pending execution or return current Resume/New choices. A user-selected New gets a fresh request ID and `intent: 'new'`; retrying an ambiguous transport failure repeats the exact request and ID. Setup or source-revision conflicts require a fresh source projection and inspection, then a new explicit confirmation even when the refreshed consumer reports no confirmation for ordinary first starts. A now-disabled item returns to its refreshed menu. These decisions belong to the shared host; adapters must not retry admission or recreate a session themselves.

### Reserved execution metadata and Party Games attachment

For source-backed admissions the shared service retains `participant-execution-metadata/v1` with the original validated `source_ref`, optional safe `return_to`, and optional provider-authored plain-text `source_label` (nonempty, at most 120 characters, no control characters). Agenda uses `Week of YYYY-MM-DD`. A pending reuse or retry retrieves this metadata from the admitted record, never from the new request or live plan. Provider-owned full provenance remains in the source ledger. A direct admission may have no source metadata.

The server passes the retained metadata to the consumer's server-only `begin` alongside its frozen snapshot. Party Games supplies the snapshot and metadata to Gaming reserved creation. The Gaming journal retains `participant-execution-evidence/v1` (snapshot and metadata); its creation digest covers the evidence. The public Gaming header exposes only `launch.participant_launch`: `participant-session-attachment/v1`, launch ID, snapshot hash, consumer, and any compact source reference, return target, and label. The normal Gaming creation API rejects reserved-creation fields. Older journal records without evidence remain replayable.

`__app_modules/games/party-games/browser/participants.mjs` is the Party Games browser entry. The composition registry opts in exact consumer `party-games` version 1 and `party-games-launch-result/v1`; the app registry uses the same match. The adapter attaches the returned Gaming session and compares the output, explicit session, pinned definition, launch identity, snapshot hash, and frozen participants against its header. It never calls participant admission or session creation. Direct optional passthrough uses only the server's canonical target. Explicit session URLs remain authoritative over current configured rosters. A durable screen URL carries the Gaming session and the compact dated return as `return_to`; it carries no roster. The shared host still consumes the ready result's `return_to` for the live menu, and never forwards that directive to the adapter. Saved choices use the authorized Gaming projection's saved roster and source label; older sessions fall back to their available information.

The screen-host return-navigation entry maps an authenticated session header’s validated content target to a screen-root `list` and optional `focus_uid` query, or to the existing `/tv` alias when no screen is present. The screen action host passes that UID to the content menu so the dated row regains focus after document reload. These URL values request navigation only; they do not authorize content access. Party Games never interprets provider-specific content IDs. Frozen Party Games attachments mount only the explicitly registered exact experience version in their stored header and pinned definition; no current catalog row or current setup is needed. Unsupported or inconsistent versions fail closed.

The installed Agenda runtime shares one People directory, repository, participant registry and launch service. The content target resolver consults an optional source-owned `describeParticipantAction(item, action)` descriptor for the exact item and action; absent declarations remain ordinary. It never trusts client capability claims. Gaming discovery replays the verified durable journal without repairing a missing snapshot; explicit resume may repair it.

Legacy ownership is an exact composition-injected decision, independent of enabling Agenda. The neutral `GET /api/v1/list/_ownership/:kind/:id` lookup exposes only an authorized owner and canonical content ID when claimed, or null when unclaimed. An unavailable authority fails closed. Legacy list reads and mutations consult the same object; transferred writes return `resource_moved`. Screen deep links consult the lookup and use the existing source host for claimed targets; a configured route may set `persistPath: true` to retain its path. The installed durable migration authority serializes transitions with actual legacy-store commit guards and the repository series lane. Configured missing/corrupt authority fails closed. Staged canonical menus and new launches remain unavailable until ownership changes; retained game resume stays independent. See `__docs/runbooks/agenda-migration.md` for the authenticated CLI, maintenance-window activation order, and recoverable phases.

The legacy list create guard resolves the same canonical name used by list storage before checking ownership, including case, whitespace and punctuation normalization. Embedded lists reject multiple effective action representations before plan or request receipt writes; equivalent watchlist and legacy encodings of the same target remain supported. Screen composition retains the existing durable `fhe` suffix as a compatibility default when no `persistPath` is specified; an explicit route policy takes precedence.
