# RetroArch per-game overrides (Shield)

Games launched on the living-room Android TV run in **RetroArch**, not in the
browser emulator. This page covers the one RetroArch behaviour the household
config controls per game: whether a game **boots back into its last savestate**.

## The rule

- **Auto-load is off by default.** The global `retroarch.cfg` on the device has
  `savestate_auto_load = "false"`. A game starts at its title screen, so a player
  can always get back to the start. Before this change, every game reopened
  mid-level from the last exit snapshot, which made games like Sonic unusable.
- **Auto-save stays on** (`savestate_auto_save = "true"`). A snapshot is still
  written on a clean exit and can be loaded deliberately from the RetroArch menu.
- **Battery-save games are unaffected.** Pokémon, Zelda, Mario Kart and similar
  titles keep their in-game saves (`.srm`) either way.
- **Opt a game in** only when it has no other way to keep progress.

## Config

`household/gaming/retroarch/catalog.yml`. The `games:` list is regenerated by
the RetroArch sync, but `overrides:` survives it, so the flag lives there:

```yaml
overrides:
  gb/super-mario-land-world-rev-1:
    resume: true          # absent or anything but true = false
```

`household/gaming/games.yml`:

```yaml
launch:
  game_overrides:
    device: <device-id>                       # ADB endpoint = this device's content_control.fallback
    config_dir: /storage/emulated/0/RetroArch/config
consoles:
  gb:
    core: gambatte_libretro_android.so
    core_name: Gambatte                       # libretro library_name = override subdirectory
```

`core_name` has to match the directory RetroArch itself creates under
`config_dir`, which is the core's `library_name` (for example `Gambatte`,
`Snes9x`, `Genesis Plus GX`, `Mupen64Plus-Next`, `FCEUmm`, `mGBA`,
`dolphin-emu`). Check the device's `config_dir` listing when adding a console.

## How it reaches the device

RetroArch reads a **game override file**,
`<config_dir>/<core_name>/<rom basename without extension>.cfg`, on top of the
global config when that game loads. The Android launch intent cannot carry
per-launch config, so this file is the only per-game lever.

- **On every launch.** `LaunchService` calls a `prepareLaunch` hook before both
  the ADB launch (`POST /api/v1/launch`) and the FKB hand-off
  (`GET /api/v1/launch/intent/:id`). For a `retroarch:` item it sets the file's
  `savestate_auto_load` line to the game's `resume` value over ADB
  (`RetroArchGameOverrideWriter`). The write is idempotent: the file is read
  first and rewritten only if that line differs. Every other key in the file is
  preserved.
- **Best effort.** ADB-over-WiFi does not survive a reboot of the device, so
  the hook never throws and never holds a launch for more than 3s. On failure the
  game launches with whatever file is already there. Look for
  `retroarch.override.prelaunch` / `retroarch.override.failed` (warn) in the log
  store.
- **In bulk.** `cli/retroarch-overrides.cli.mjs` plans or writes every catalog
  game in one pass. Run it inside the container, where both adb and the data
  volume exist:

  ```bash
  sudo docker exec {env.docker_container} node cli/retroarch-overrides.cli.mjs plan
  sudo docker exec {env.docker_container} node cli/retroarch-overrides.cli.mjs sync
  ```

  `sync` refuses while RetroArch is running (a game may be in progress); pass
  `--force` to override. It exits non-zero on any failed write or skipped game
  (for example a console with no `core_name`).

## Gotchas

- **Edit `retroarch.cfg` only while RetroArch is closed.**
  `config_save_on_exit = "true"` rewrites the global file on exit and would
  undo the change. Game override files are not rewritten on exit.
- **Override filenames must match the ROM basename exactly.** A hand-made
  `Mario Party.cfg` never applied to `Mario Party (USA).n64`. Use the CLI's
  `plan` output for the real path instead of guessing.
- Files under `config_dir` for games not in the catalog are left alone.
