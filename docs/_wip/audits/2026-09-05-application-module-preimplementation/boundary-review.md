## Ownership is separate from executable layer

| Current prerequisite group | Files | Proposed owner | Layer / constraint |
|---|---:|---|---|
| HTTP middleware, logger, IDs, runtime time and filesystem helpers | 19 | platform | System mechanics; FileIO remains prohibited to application/domain code |
| Core errors, pure time and timezone constant | 6 | platform | **Domain**, context `core`, rank 0; never reclassify as system because of ownership |
| Canvas, layout and text rendering helpers | 3 | platform | Rendering; application services consume a presentation port, not this public implementation |
| Browser HTTP/device identity, logging, WebSocket service/context and memory probe | 12 | platform | Browser runtime; preserve one intended service/context/transport graph |
| Config form/table/save controls, hooks, unsaved context and Admin path mapping | 8 | admin product | Admin-owned reusable UI; using it does not move its policy into platform |
| Household configuration naming | 1 | contracts (platform-owned) | Closed declarative-contract kind, not another executable layer or ownership category |
| Realtime publication classes | 1 | mixed; split by actual owner | Extract only GratitudeEvents; retain the four unrelated classes and their current imports |

No `shared` spelling is used as semantic evidence. The same distinction applies
to the broader design: Player is a playback capability, a generic screen host is
a screen-host capability, and an installed living-room screen is composition/a
surface. Gaming mechanisms are reusable capabilities; game rules, presenters and
environment choices keep explicit experience/environment subowners. A product
export may be reusable without promotion to platform. Their wider extractions
are not prerequisites merely because Gratitude uses shared browser transports.

### Screen host, Player and Gaming: required capability seams

The current source makes the intended taxonomy concrete, and also exposes where
the current folders are mixed. These are proposed ownership/split boundaries,
not source moves or new public APIs.

| Current surface | Proposed owner/subowner | What may be reusable | What must remain outside the generic capability |
|---|---|---|---|
| `frontend/src/screen-framework` | `capabilities/screen-host` | Widget registry, panel/layout rendering, input/action translation, overlay/PiP primitives, screen state/provider contracts and narrowly injected browser adapters | Installed-screen routing, concrete API/config acquisition, FKB/global keyboard setup, menu navigation, Surround settings, Player session registry and product widgets |
| `screen-framework/widgets/builtins.js` and the current `ScreenRenderer` startup path | installed screen-host composition/surface | A separately named, explicit registration bundle may compose supplied widgets | It is not a generic built-in package: it currently imports Time, Weather, Finance, Health, Piano, Camera, Party Games, School and School lesson/reading components, and `ScreenRenderer` calls it at module load |
| `frontend/src/modules/Player` | `capabilities/playback` | Media renderer primitives, queue/resilience/session mechanics and declared playback ports | `Player`/`SinglePlayer` currently import `AppContainer` and browser API/logging/volume/screen-session facilities. Keep that integration in a capability composition facet or inject it; do not call the present top-level component a platform primitive |
| `frontend/src/modules/Gaming/platform` | `capabilities/gaming` | Rule kernel, session authority, runtime controller, generic UI primitives and input/projection ports | Experiences, presenters, environment-specific effects and surface choices remain `gaming/experiences/*` and `gaming/environments/*`; `GamingApp` supplies presenters, while the screen's Party Games widget is installed-surface composition |

The dependency direction is therefore:

`product experience/widget → capability public API → screen/playback composition → installed surface`.

The generic capability must not import a product widget, AppContainer or a
specific room deployment. A composition surface may import both a capability and
product widgets. The present `screen-framework/index.js` re-exports
`registerBuiltinWidgets`, which loads the mixed registration graph; it cannot be
the future generic public entry unchanged. Likewise, retaining Player as a
top-level capability does not grant its current AppContainer-coupled entry
platform status. Gaming's presenter injection is the correct pattern to extend:
an owner exports mechanisms and explicit extension points, while experiences
contribute implementations through composition.

Before any extraction, freeze the existing registration names and 16 built-in
widget population from `registration-review.md`; test the generic entry with no
product-widget imports and the installed composition entry with the exact current
registration population. The latter remains responsible for existing URL,
keyboard, session and kiosk behavior. This decision blocks a broad alias-only
relocation and prevents D1/D2/D3 violations through hidden composition imports.

## Entry and import decisions

1. Preserve current default/named spelling and aliases. The candidate mapping
   records each original imported/local/exported name. For example the system
   utility barrel's `ShortId` is an alias of `IdUtils`; replacing the module must
   not look for a nonexistent `ShortId` declaration in the leaf file.
2. Split imports from the broad system utility barrel by their real origin.
   A clock-only caller should not inherit the barrel's FileIO loading closure.
   This is an explicit later import rewrite, not a claim that tree shaking makes
   the current runtime import safe. Namespace, side-effect and `export *` users
   need their own review; they are not silently converted to named imports.
3. The 49 proposed file-level entries are a review index, **not an instruction
   to publish all 49**. Keep owner-internal helpers private wherever possible;
   approve only the entries with actual external consumers. Test-reset controls
   need test-only visibility. Reject mixed-layer or mixed-owner barrels.
4. Ordinary cross-owner consumers use public entries. Same-owner implementation
   files can use local relative paths or facet-local `#` aliases, subject to the
   same layer/subowner rules. Existing `#system/*` aliases cannot simply be
   retargeted wholesale when most of that directory has not moved: each affected
   exact import/mapping must be specified, and all unaffected mappings retained.
5. Every facade retains its target layer and complete loading closure. A named
   re-export of a pure helper from a clocked/system module does not turn the
   whole loaded module into a pure contract. D1–D10 remain binding.

## State, resources and remaining decisions

One product-owned boundary now has an exact selected spelling:
`@daylight/gratitude/server/adapters/image-print-gateway`. It forwards the default
and named `TemporaryImagePrintGateway` exports from the Gratitude server facet's
`./image-print-gateway` subentry. `owner-boundaries.json.publicEntries` records the
exact facade, manifest entries and forwarding source; `import-replacements.json`
records its five affected source edges. This is specification, not an installed
package or authorization to execute the move.

The implementation and its real `IImagePrintGateway` application port stay with
Gratitude. Fitness composition consumes the public adapter; Gratitude composition
uses its owner-internal relative path. Applications receive the injected print
operation and cannot import the concrete adapter. The public facade keeps the
adapter layer and does not expose the private port. Generic print drivers/fleet
remain outside Gratitude. Native resolution, FileIO instance identity and the
existing raw `path` prohibition and OS-temp capability ownership still gate
implementation. The guidance explicitly names `path`, not an `os` ban.

The Feed query has a selected [operation boundary](feed-boundary.md), not a
separate `server/queries` module export: the public composition factory returns
`gratitudeQueries.readSelectionQuotes`, injected into Feed as `readGratitudeQuotes`.
Gratitude's private port/read adapter/query and exact constructor/factory changes
are specified in `feed-boundary.json`. A local lazy iterable preserves selected-
row/error timing; it is not a new DTO or wire protocol. No application/adapter
permission is gained through the returned operation. Twelve baseline cases pass;
the planned implementation itself is not executed or approved for migration.

The [Homebot command boundary](homebot-boundary.md) similarly exposes a returned
operation, `gratitudeCommands.addSelections`, without an unused `server/commands`
entry. Homebot composition supplies it through a Homebot-owned adapter that
extends its consumer-owned application port; no container imports an adapter.
Eleven original-source command/batch cases and three projection contrast cases
pass. The exact command changeset is specified; additional negative controls
and native candidate proof remain open.

The [household boundary](household-boundary.md) now specifies its own shared
source port, extending config adapter, application presentation query and two
public composition/browser facades. Config representation stays in the adapter;
category and timestamp/fallback policy stays in Gratitude. The web client returns
the original roster-response request promise at the existing URL without extra
async/caching/normalization. Nine server/five browser baseline cases pass. Exact
core source/manifest proposals do not complete global metadata/target/lock/build
or native package identity gates.

Browser Logger/sharedTransport/WebSocketService form an existing dynamic cycle.
Their migration must preserve one intended service and logger transport, not
construct per-owner instances. `WebSocketContext` and Admin's
`UnsavedGuardContext` each require the provider and consumers to resolve the
same context object as well as the same React. The actual dependency probes
demonstrate both different-React failure and same-React/different-context failure.

FileIO also has identity and effect constraints: a module-level directory cache,
captured YAML/HTTP dependency scope and indirect IO defaults/callbacks. The
[storage binding review](storage-consumer-review.md) accounts for all exports and
direct/barrel consumers, including 51 production function references that are
not direct calls. Its image-download boundary is not equivalent to a pure YAML
store. Preserve actual primitive behavior and path suppliers when approving the
public entry; D5/D10 still prohibit direct application/domain imports.

`CanvasFactory` computes its default font directory relative to its source URL.
Moving that file changes the meaning of the current relative URL. Nine tracked
font/license artifacts are identified in `additionalResources`, beyond the
50 JavaScript foundation candidates. Review all consumers before moving the
canonical font authority or explicitly retaining it; preserve deployment override
semantics, font bytes/licenses and the backend native-canvas instance. Do not
accept a silent system-font fallback as parity.

The next boundary review must still approve each externally exposed entry,
classify namespace/all imports and their loading effects, verify the selected
Feed query and finalize other bindings, and connect every affected consumer to
its acceptance population.
The proposed file/symbol mapping makes those reviews concrete; it does not
substitute for them. The 31 Gratitude candidate moves and 66 directly affected
Gratitude edges remain in `owner-boundaries.json` and `import-replacements.json`.

## Proposed owner-metadata field contract

This describes the later `owner.json`, not a new production file or loader.
Metadata revision and values are checked by architecture tooling; the owner
cannot grant itself exceptions.

| Field | Required meaning / validation |
|---|---|
| `schema` | Fixed supported revision; unknown revisions fail closed |
| `id`, `category` | Globally unique kebab-case owner ID; product/capability/platform; reserve platform and contracts |
| `root`, `facets` | Canonical owner root plus explicit sibling public/server/web/other package paths; no ancestor workspace enclosing facet workspaces |
| `subowners` | Named internal experience/environment/common boundaries with canonical non-overlapping assignments and explicit public access |
| `contexts` | Exact path→domain-context mapping; rank read from authoritative policy, never supplied as self-approved permission |
| `classifications` | Runtime, executable layer or reviewed declarative kind, production/test/tool/resource status per path; unknown/overlapping matches fail |
| `publicEntries` | Semantic annotations keyed by the exact package export and symbol, target source/subowner, contract IDs, instance requirements; resolve targets from package manifests |
| `devTargets`, `testTargets` | Explicit commands, runtime, fake-port/fixture requirements and expected runner ownership; not app activation |
| `satellites` | References to independent source/build/operator paths and logical ownership; do not automatically add those manifests to npm workspaces |

Dependencies and actual export paths remain in facet manifests. Metadata does
not duplicate an authoritative dependency list, enable apps, instantiate providers,
choose game experiences or replace current config/catalog registration. Changes
to classifications require architecture review; unknown ranks or D10 violations
block affected moves without a grandfathered baseline.
