## 4. The `.env` question (task R3)

**Verdict: the symlink fixed it. No env export is required.**

- `<worktree>/.env -> <main-checkout>/.env` — the symlink resolves, is readable, and contains
  `DAYLIGHT_BASE_PATH=…`. (`.env` is untracked, so it exists only in the main checkout; that is
  why the worktree needed the link at all.)
- Both previously-failing tests now pass:

| File | Runner | Result |
|---|---|---|
| `backend/tests/unit/system/config/registryCompleteness.test.mjs` | **vitest** — no runner import, bare top-level `it(`, so `globals: true` supplies it and `isVitestOwned` claims it | `Tests 3 passed (3)` |
| `tests/unit/content/singalongStoredShape.test.mjs` | **vitest** — imports `{ describe, it, expect } from 'vitest'` explicitly | `Tests 2 passed (2)` |

Neither file appears anywhere in either sweep log (the reporter prints only failures), and both
pass solo.

**Correcting a prior assumption:** the earlier `No test files found` when running
`tests/unit/content/singalongStoredShape.test.mjs` under vitest did **not** mean the file is
Jest-owned. `tests/unit/harness.mjs` (Jest) collects **only** `tests/unit/suite/`
(`const suiteDir = join(__dirname, 'suite')`), and this file is not under `suite/`. It is
vitest-owned by explicit import, and it is in the gate population. That earlier result was a
bad invocation, not an ownership fact.

**Why the symlink is sufficient — and the one prerequisite it implies.** Both files resolve the
data dir with the same fallback ladder: `DAYLIGHT_DATA_PATH`, then `DAYLIGHT_BASE_PATH`, then
parse `path.join(process.cwd(), '.env')`. The third rung is what carries them, and it keys off
**`process.cwd()`**.

> **Prerequisite for every later task:** run tests with the **worktree root as cwd**, and keep
> the `.env` symlink in place. Neither is optional — a run launched from elsewhere silently
> loses the data path and these tests fail with
> `no data path — set DAYLIGHT_BASE_PATH or DAYLIGHT_DATA_PATH`.

If the symlink is ever lost, the equivalent explicit export is:

```bash
# take the value from DAYLIGHT_BASE_PATH in the main checkout's untracked .env
export DAYLIGHT_BASE_PATH="<the path that .env sets>"
```

(`DAYLIGHT_BASE_PATH` takes precedence over `DAYLIGHT_DATA_PATH`; set only one.)

A task's test run is clean if the only failures are on this list.

**Ignore — STABLE-PREEXISTING (5 files, 12 tests).** All five are already in
`scripts/audit-baseline.vitest.txt`, so a green gate covers them automatically:

- `backend/src/1_adapters/glossika/LegacyDumpReader.test.mjs`
- `backend/src/4_api/v1/agents/mountAgentHttp.test.mjs`
- `backend/src/4_api/v1/agents/wireFormats/native.test.mjs`
- `backend/src/4_api/v1/routers/piano.effect-audit.test.mjs`
- `backend/src/4_api/v1/routers/piano.loop-manifest.test.mjs`

**Ignore — ROAMING FLAKE, but only after a solo re-run passes.** The six files in §2 are the
observed victims; the set is not closed, and the next sweep may pick a different one. The rule
is the procedure, not the list: *any* single failing file that passes when run alone is a flake.

**Ignore — everything outside the gate population**: `tests/live/**`, `tests/integrated/**`,
`tests/integration/**`, `tests/applications/**`, `_extensions/**`, `backend/shared/**`, and the
526 `(0 test)` `node:test` files. No gate covers them and none are this feature's concern.

**Do NOT ignore:**

- Any failing file in the gate population that is not in `audit-baseline.vitest.txt` **and**
  still fails solo. That is a regression.
- Any gate-population file that starts reporting `(0 test)`. The count is **0** today, so any
  nonzero value is new — and it is the failure mode that already bit this feature once.
- Any drop in `pauseArbiter.test.js` (15) or `governance-video-pause.unit.test.mjs` (14) test
  counts. Those numbers are the guard against a silent unhook.

**Because gate run 1 was red on unmodified code, one red gate run is not a regression report.**
Re-run the gate, then re-run the named file solo. Escalate only if it fails alone.
